## Problem Summary

`sonos play` (src/sonos_cli/cli.py `cmd_play`) plays local files on a Sonos room, but only while a foreground command keeps its temporary `TrackServer` (src/sonos_cli/server.py) alive. Its track URLs are random in-memory tokens, so they die with the process even though the speaker keeps the queue. There's no UI, no playlists, no room management and no way to play browser audio. This spec turns the tool into an always-on background service with a LAN web UI, playlists, room management, page sending (direct audio links, first of all the user's Faircamp site) and live Chrome tab streaming. It targets five Sonos S1 players: Office, a Play:1 stereo pair with 192.168.0.21 as coordinator and .27; Bedroom .31; Kitchen .29; Lounge .26.

### Must Have

On a fixed port (default 8737, configurable), on all interfaces, it serves the web UI, a JSON API and the audio rooms fetch. `GET /api/health` reports `ffmpeg: ok|missing`, `rooms_seen: N` and the service's host and port. — AC: with the service running, `/api/health` answers 200 from `127.0.0.1` and from the Mac's LAN address, and reports `ffmpeg: missing` when ffmpeg can't be found. `[integration]`

After `kill -9` of the service, it's healthy again within 10 s. After `uninstall`, no plist and no listener on the port. `[unit]` for the plist, the install flow against a fake `launchctl`, and the launcher; `[user]` for the real agent (epic 01-08 Story 7), since installing a persistent LaunchAgent isn't something the build session may do.

- **FR4**: A RoomMonitor (AD8) discovers rooms at start-up and every 60 s off the request path, and on demand. It identifies rooms by UID (`RINCON_…`). `GET /api/rooms` returns each room's UID, name, coordinator UID and IP, model, group members, transport state, volume and mute, from the monitor's cache. — AC: the room list matches a stubbed discovery result, a refresh picks up a changed IP and a renamed room under the same UID, and `/api/rooms` answers without calling SoCo. `[unit]`
- **FR5**: `POST /api/play` takes a room UID, a list of local paths (files or folders) and a mode (`replace` or `append`), then queues and plays them on the room's group coordinator. Each track's URL is stable (AD7). Folders expand in name order, capped at 500 tracks with a note in the response. The first track is probed and starts playing before the rest are probed and queued in the background. Dataless (online-only) Dropbox placeholders are skipped with a reason and never read. Conversion follows the existing rules (`media.needs_conversion`, `media.convert`) and happens lazily on the first fetch. A file that is converted is queued under a URL ending `.flac` (`hires.wav` as `hires.wav.flac`; a hi-res `.flac` keeps its name), because an S1 judges a stream by the extension of its URL and refuses FLAC served as `.wav` (found on the real Office, docs/quick/04-quick-converted-files-need-a-flac-url.md). — AC: a mixed folder (16-bit WAV, 24-bit/96 k WAV, MP3, one fake dataless file) is queued in name order, has the right MIME types, serves the hi-res file as 16-bit FLAC and skips the placeholder with a reason. `[integration]`
- **FR6**: Every file path the service accepts or serves is resolved with `realpath` and must be `is_relative_to` a resolved allowed root: music folders, the cache directory or the playlists directory. This applies to stable media URLs, `/api/play` paths, the browse path, playlist names and M3U entries. Filenames are compared after Unicode NFC normalisation. A path outside the allowed roots is refused with 403. — AC (refused): `/etc/hosts`, `<music>/../secret.txt`, `..%2f` and double-encoded `%252e%252e%252f` traversal, `<music>/link-to-home/x.wav` (a symlink pointing outside), the sibling-prefix path `<music>2/x.wav`, the playlist name `../../x`, and an M3U entry `/etc/hosts`. - **FR7**: A file inside the allowed roots is served when requested through a music root that is itself a symlink (as `~/Dropbox` is). The same applies to `Café – Ünïcode 日本.wav` requested in NFC and in NFD. — AC: these floor cases return 200 with the right bytes. `[integration]`
- **FR8**: The existing CLI commands (`play`, `pause`, `resume`, `stop`, `next`, `prev`, `volume`, `status`, `rooms`) go through the service API whenever `127.0.0.1:<port>` accepts a connection. Any API error is reported, not hidden by a fallback. Only when the connection is refused do non-play commands use SoCo directly and `play` use the in-process path. `play` and the service share one core: path expansion, probe, convert, queue-item building and stable URLs (AD3). `play` turns paths into absolute ones. Transport, queue and volume act on the group coordinator. — AC: against a fake system including an invisible stereo-pair satellite, the API calls `player_name` set / `join` / `unjoin` / `partymode` on the right device, and `partymode` leaves the satellite alone. After a rename, the same UID still plays. `[unit]`

Tracks whose files are missing, or outside the allowed roots, are shown as unavailable and skipped on play. — AC: a playlist with a non-ASCII track survives a service restart and round-trips through M3U, and playing it skips a deleted file and an outside-roots entry. `[unit]`
- **FR13**: `POST /api/send` takes a room UID and either a page URL, which the service fetches, or page HTML plus its base URL, which the extension sends. It extracts audio the room can play natively and queues it on the room. Per the AD5 amendment (spike 01-01 Story 2), S1 can't fetch the site's HTTPS URLs, so each is queued as a `/remote/…` proxy URL on this service. A page with nothing playable gives a clear error. `sonos send <url>` and a UI URL field use the same endpoint. — AC: saved copies of a shtl-experiment.com release page and of a generic page (with relative, space-containing and non-ASCII URLs) give the expected ordered list of absolute, percent-encoded tracks, with no Opus URLs. `[unit]`
- **FR14**: A Chrome extension (Manifest V3, loaded unpacked from `extension/`) has a popup that lists rooms from the service and remembers the last room by UID. When the popup opens, it sends the current page's rendered HTML to `POST /api/send/preview`. It shows **Send page** if the preview finds tracks within 2 s, and **Checking…** then **Stream tab** otherwise. It offers **Stream tab** / **Stop** on every page. — AC: on a local test page with direct MP3 links the popup offers Send page, and on a page without them only Stream tab. The chosen room is remembered across popup opens and across a rename of that room. `[browser]`
- **FR15**: Tab streaming. The extension's offscreen document captures the tab (`tabCapture` stream ID → `getUserMedia`), runs an `AudioContext({sampleRate: 48000})` with an AudioWorklet producing 16-bit stereo PCM, and sends it over a WebSocket to `/live/ingest?room=<uid>`. The service encodes it once with ffmpeg (MP3 320 kbps CBR) into a live stream the room plays as `x-rincon-mp3radio://<mac-ip>:<port>/live/<id>.mp3` (AD4). Streaming state lives in the offscreen document, so the popup can close. Only one stream runs at a time. The stream ends when the user clicks Stop, when the tab closes, or when the room switches to another source; the extension is told which. — AC: on a test page playing a 440 Hz tone, Stream tab produces `/live/<id>.mp3` that decodes to 440 Hz ± 5 Hz, and closing the tab ends the stream within 5 s. `[browser]`
- **FR16**: The live stream serves listeners from a shared buffer. — AC (all with fake rooms): a listener joining mid-stream gets decodable MP3 starting on a frame boundary. A listener that stops reading doesn't stall a second listener. Responses carry no chunked encoding and no `icy-metaint`. A listener that reconnects within 10 s gets audio again. Ingest running 60 s with no listener doesn't grow memory beyond the buffer. When ingest closes, `/live/<id>.mp3` ends rather than hanging. When the fake room's URI changes to another source, ffmpeg exits within 5 s, leaving no orphan ffmpeg process. `[integration]`

This includes a pause of up to 30 minutes (configurable). Another Mac's URLs don't count. FR13's `/remote/…` proxy URLs are ours, since the Mac serves the bytes (AD5 amendment). The assertion is released within 30 s of nothing of ours playing. — AC: the assertion is held for a PLAYING room on our URL and for a room PAUSED on our URL within the grace period. It isn't held for another host's URL or a grouped member reporting `x-rincon:`. It's released within 30 s of STOPPED. With the release step removed, it stays held (control). `[unit]`

## Non-Functional Requirements

- **NFR1**: From an API play call on a natively playable local file to Office reporting PLAYING, the median of 5 muted runs is 3 s or less. Measured with the live-test helper. `[manual]`
- **NFR2**: Live tab streaming delay of 6 s or less, tab to speaker, judged by the user by ear (no measured figure required; amended 2026-11-04 at the user's choice). A click track filmed with the tab and the speaker together remains the way to measure it if a figure is wanted. Spike 01-01 Story 2 gave a first figure from the encoder's output byte count and the time to PLAYING. **First figure (2026-11-03, Office, prototype of AD4 fed from a WAV):** ingest to send is 0.04–0.12 s (ffmpeg MP3 320 encode, 70 s run), the 8-chunk startup burst is about 0.26 s of audio (chunks were about 1.3 KB at 31 per second, from `proto.log`), and the Sonos buffer is about 3.3–4.3 s (PLAYING 4.28 s after `play_uri`, polled once a second). The ingest figure is an estimate from the output byte count against the MP3 bitrate, not a marked-frame measurement, and it is effectively encoder latency. The total is roughly 3.6–4.7 s tab to speaker (the buffer figure includes the SOAP call and the wait for the first GET, so it errs high) before the browser's own capture latency, so the 6 s budget has about a second of room. The startup burst is the one knob the service controls: use the smallest that doesn't underrun. `[user]`
- **NFR3**: Idle service under 150 MB RSS and averaging under 1% CPU over 5 minutes. Measured with `ps` on the installed agent with no UI open, and again with one UI tab polling. `[user]` (epic 01-08 Story 7).
- **NFR4**: Installation needs only Python 3.12+ and uv. **Amended (2026-11-03, the user):** ffmpeg is bundled with the package (the `imageio-ffmpeg` wheel; no ffprobe, ffmpeg probes files itself) instead of needing Homebrew, and the launcher app for `sonos service install` ships prebuilt instead of needing the Xcode command line tools (epic 01-09). A config-path ffmpeg still wins; the bundled copy comes before a Homebrew one on `PATH`, so every Mac runs the same build unless the user says otherwise. The UI and extension have no build step.
- **NFR5**: After a speaker changes IP, the service finds it again within 60 s without a restart (unit test with fake discovery), and after a speaker is unplugged and replugged. `[unit]` + `[user]` (unplugging is the user's check, epic 01-08 Story 6)
- **NFR6**: Browser-origin hardening (no login, but no drive-by control):
  - A request whose `Host` isn't the Mac's IP, its hostname, `localhost` or `127.0.0.1` is refused (stops DNS rebinding).
  - Every state-changing request, and every WebSocket upgrade, must carry an `Origin` that is the service's own or `chrome-extension://<configured id>`.
  - State-changing requests must be `Content-Type: application/json`.
  - Speakers fetching media (no `Origin` header) are unaffected.
  - AC: a forged Host, a forged Origin on POST and on the WebSocket, and a `text/plain` POST are each refused. The same requests are accepted with the checks removed (control). `[integration]`

## Architecture Decisions

### AD1: One Python service built on Starlette + uvicorn
The service is one process hosting the API, UI, media serving and the live WebSocket. It has `FileResponse` with Range support and raw ASGI responses where streaming needs control over headers (AD4). Blocking SoCo calls run in a thread pool, and only the RoomMonitor makes them for reads. Alternatives: the stdlib `ThreadingHTTPServer`, which has no WebSockets, or aiohttp, which would work equally well.

### AD2: UI is static HTML + vanilla JS, no build step
Shipped in `src/sonos_cli/web/`. It polls `GET /api/rooms/{uid}/state`, served from the RoomMonitor's cache, every 2 s.

### AD3: Shared playback core; the CLI is a thin client with one narrow fallback
`media.py`, a new `library.py` (path expansion, guard, stable URLs) and `player.py` form the core both paths use. The in-process `TrackServer` is reimplemented on the core and kept only for when the service isn't listening (FR8), so fixes aren't made twice.

### AD4: Live streams: PCM in, MP3 out through a ring buffer

- **One stream per room.** A live-session registry keyed by room UID; starting a new stream for a room replaces the old one.
- **Ingest.** PCM (s16le, 48 kHz, stereo) over the WebSocket is piped to ffmpeg, which encodes MP3 320 CBR. A reader always drains ffmpeg's output into a bounded ring buffer of MP3 frames, dropping the oldest, so ffmpeg never blocks.
- **Listeners.** Each starts at a frame boundary a short burst behind the live edge, with its own bounded queue, and a slow listener drops frames rather than stalling others. Responses are HTTP/1.0-style: `Content-Type: audio/mpeg`, no Content-Length, no chunking, `Connection: close`, and no ICY metadata.
- **Control.** Messages on the ingest socket tell the extension `ended: stop|tab-closed|room-switched|replaced|service-error` (`replaced`: another stream was started for the same room). The extension tells the service why it is stopping with a text message `{"end": "stop"|"tab-closed"}`; the service then stops the room too if it is still playing that stream.
- **Encoder start.** ffmpeg is started with `-fflags nobuffer -analyzeduration 0 -probesize 32` and `-reservoir 0`: without them it waits for about 5 s of PCM before encoding anything (found in Story 01-07/1), which both delays the stream and breaks any shorter feed.
- **Starting the room.** The ingest socket answers `started` as soon as the stream exists, and the service tells the room to play it alongside: a real S1 speaker answers that request only once it has audio to buffer, and the audio can't flow until the client has been told to start (found on the Office, 2026-11-03: the first version waited for the speaker and timed out after 10 s). A refusal arrives afterwards as `ended: service-error` with a detail.
- **Real speaker (Office, 2026-11-03, tab streamed through the extension).** PLAYING 6.0 s after clicking Stream tab; the position advanced steadily for the 60 s hold; Stop to not-PLAYING in 0.5 s. The speaker reports the stream's media URI as `x-rincon-mp3radio://<ip>:<port>/live/<id>.mp3` but its *track* URI with the scheme twice (`x-rincon-mp3radio://http://<ip>:<port>/…`), so `classify_source` accepts both.
- **Listener sockets.** `GET|HEAD /live/<id>.mp3` is answered by a uvicorn protocol subclass (`live.protocol_for`) before uvicorn's HTTP layer: uvicorn answers an HTTP/1.1 request with no length as `Transfer-Encoding: chunked`, and Sonos sends HTTP/1.1. Each listener socket gets a 64 KB send buffer so a stalled reader backs up into its own bounded queue.
- **Spike first.** Spike 01-01 Story 2 proves Office plays `x-rincon-mp3radio` from this design, fed from a WAV, before any extension work.
- **Spike result (2026-11-03).** Office stayed PLAYING for 70 s on `x-rincon-mp3radio://<mac-ip>:<port>/live/test.mp3` with raw-socket HTTP/1.0-style responses (no Content-Length, no chunking, `Connection: close`) and no reconnects. Sonos (`Linux UPnP/1.0 Sonos/57.23-74170 (ZPS1)`) makes two GETs and no HEAD: a first probe with `CONNECTION: close` that it closes within about 65 ms, then the streaming GET with `Icy-MetaData: 1`. Both get the same stream, so the server must accept and tolerate the first connection dropping. It sends no `Range`. Header names arrive in mixed case (`CONNECTION`, `ACCEPT`, `HOST`), so parsing is case-insensitive. Position advances in real time, and PLAYING comes about 4.3 s after `play_uri`.

### AD5: Remote audio is proxied through the service
**Amended**: 2026-11-03 — spike 01-01 Story 2 showed S1 can't play the site's HTTPS URLs, so remote audio is proxied (also changes FR13, FR17, AD7, NFR2's first figure and AD4's spike result).

The first plan was to queue remote HTTPS URLs directly so the Mac isn't needed during playback. On Office (firmware 11.16.1), `https://shtl-experiment.com/hello-ep/1/mp3-v5/…/01%20Halyard.mp3` queued with `add_to_queue` or sent with `play_uri` stays STOPPED with an empty title. The plain-`http://` form fails as well, but the site answers it with a 301 to https, so that result adds nothing beyond the https one (it isn't shown whether Sonos follows redirects). `x-rincon-mp3radio://shtl-experiment.com/…` and `x-rincon-mp3radio://http://…` were refused with UPnP 701; neither tested HTTPS, so they don't add to the finding. The site's certificate is Let's Encrypt (issuer YE2, TLS 1.3, seen with `curl`), and the likely cause is S1's old TLS root store, but the cause isn't confirmed.

So FR13 queues `http://<mac-ip>:<port>/remote/<signed token>`, and the service fetches the https URL on request. The Mac must be on while it plays.
- **Token.** It carries the remote URL and an HMAC of it under a per-install secret stored in the config directory, so a URL stays valid across restarts with no server-side state.
- **Not an open proxy.** The service fetches only URLs it signed. Signing happens in `/api/send`, which any LAN client can call (no login), so the proxy also refuses non-http(s) schemes and any URL whose resolved address is not public (loopback, private, link-local), checked at fetch time and again on every redirect.
- **Range.** `Range` is passed through to the origin.

### AD6: launchd agent runs through a small signed app bundle
**Amended**: 2026-11-03 — spike 01-01 Story 1 chose the wrapper bundle.

The plist runs a fixed executable with `KeepAlive` and `RunAtLoad`. Logs go to `~/Library/Logs/sonos/service.log`. The executable is a small ad-hoc-signed app bundle (`SonosService.app`, bundle id `local.sonos-cli.…`, `NSLocalNetworkUsageDescription` and `NSBonjourServices` in its Info.plist) whose Mach-O launcher spawns the uv tool's Python as a child and waits (`tests/launchd_probe/launcher.c`). Local Network permission is then held by the bundle, not by the Python binary.

Evidence (Office session, 2026-11-03, probe agents started by launchd; Python's parent is launchd (`ppid 1`) for A and the launcher for B; screen unlocked, and you reported granting every permission pop-up, without naming them):
- Python run directly by launchd (variant A): discovery, an HTTP GET to the speaker, `ffprobe` and a read from `~/Dropbox` all worked after the grant. A copy of the same Python at a new path also worked, so moving or recreating a venv is harmless. ### AD7: Stable, stateless media URLs

- **Form.** Local tracks are `/media/<root-id>/<percent-encoded path relative to the root>`, where `root-id` is a short hash of the resolved root; a file that is converted to FLAC before it is served has `.flac` added to that path (`hires.wav.flac`), since an S1 judges a stream by its URL's extension (docs/quick/04). Every request re-resolves the path, guards it (FR6), and converts it if needed (cached by the existing `cached_conversion_path` key). A service restart therefore never breaks a queue.
- **Host.** URLs carry the Mac's LAN IP, because S1 can't resolve `.local`. An IP change still breaks queued URLs, so the README recommends a DHCP reservation for the Mac.
- **What counts as ours.** A URL is "ours" when its port is this service's port, its host is one of this Mac's addresses, and its path starts with `/media/`, `/live/` or `/remote/` (AD5 amendment).

### AD8: RoomMonitor owns room state; Sonos owns queues and groups
One RoomMonitor per service does discovery and polls each room that a UI is watching, or that is playing something of ours, every 2 s (every 6 s while a room is doing nothing, including one that has stopped answering: a watched, stopped room read every 2 s cost over 1 % of a core, found by the user check in epic 01-08 Story 7, 2026-11-03). It caches the state and publishes changes to the UI API, the live sessions (FR15's room-switched) and the sleep assertion (FR17). The service keeps no copy of queues or groups. The only state it owns is config, playlists, the conversion cache and live sessions.

## Multiple Macs

Each Mac may run its own service. Each serves, and keeps awake for, only its own URLs (AD7). The UI labels sources served by another host. A "replace" from one Mac replaces whatever the room was playing, including another Mac's queue; that's the expected Sonos behaviour. A laptop with its lid closed sleeps whatever assertion is held, and its queues then stop. Use the Mac that stays awake as the host for long sessions.

## Testing Strategy

- Test command: `uv run pytest`.
- `[unit]`: pytest with SoCo replaced by an in-memory fake system (`tests/fakes.py`: rooms, groups, an invisible satellite, queues, transport state). No network.
- `[integration]`: pytest that starts the Starlette app (in-process with `httpx`/`TestClient`, or uvicorn on an ephemeral port for raw streaming and WebSocket tests) against fake rooms, with real ffmpeg/ffprobe and generated test tones.
- `[browser]`: `do` drives the web UI with claude-in-chrome against `sonos service run --fake-rooms`. It drives the extension through the harness chosen in spike 01-01 Story 3 (`tests/extension_harness/`), since loading an unpacked extension and granting tab capture can't be done through claude-in-chrome. The method, proven on Chrome 156 on 2026-11-03: launch branded Chrome with a throwaway `--user-data-dir`, `--remote-debugging-port`, `--enable-unsafe-extension-debugging`, `--allowlisted-extension-id=<id>`, `--auto-accept-this-tab-capture` and `--autoplay-policy=no-user-gesture-required`; load the extension over CDP with `Extensions.loadUnpacked` (Chrome 156 ignores `--load-extension`, even with `DisableLoadExtensionCommandLineSwitch` disabled); pin the extension ID with a `key` in the manifest so the allowlist flag can name it; then start a capture by evaluating the extension's `startCapture(tabId, sink)` in its service worker through CDP. Without the allowlist flag `getMediaStreamId` fails with "Extension has not been invoked for the current page". The spike streamed a 440 Hz tab in the background for 60.9 s to a WebSocket sink: 48 kHz stereo, no gap over 43 ms, 440.0 Hz in the first, middle and last 5 s. Local test pages are served by the test harness (a page with MP3 links, a page playing a 440 Hz tone). Live speakers are never needed for `[browser]`.
- `[manual]`: `do` runs the step in the session, e.g. launchd install or a live check on Office through `tests/live.py` (FR18).
- `[user]`: only the user can prove these, because they involve hearing the speakers, their phone, a real shtl-experiment.com page or YouTube in their own Chrome. They're all in the final user-checks epic.
- **Live-test rules**: anything that touches a real room uses Office through `tests/live.py`. It mutes every member first and restores volume and mute in a separate `finally` before the queue or source. (In the 2026-11-02 session, restoring a Spotify Connect source raised UPnP 402 and skipped the rest of the restore.)

## Assumptions

- "This Mac" for FR23 means the connection's peer address (the TCP peer, never a header, and uvicorn is started with `proxy_headers=False`) is loopback (127.0.0.1, ::1, or an IPv4-mapped form of either) or equals the address the connection came in on (`scope["server"]`), so the UI opened on the Mac through its LAN IP can change folders too (the user's choice, 2026-11-03). It needs no address lookup and no cache, so nothing another device registers in DNS or DHCP can make it count (found by the Story 8 audit: a first design trusted `getaddrinfo(hostname)`). A request that reaches the service through a local forwarder (`ssh -L`, `tailscale serve`, Docker's host forwarding) arrives from loopback and counts as this Mac; that is accepted. Folder browsing lists folder names only (no files, no hidden folders) under the home folder and `/Volumes`; a pasted path may be anywhere readable. The user chose this-Mac-only over LAN-wide browsing and over paste-only (2026-11-03).
- Adding or removing a music folder has no CLI command; `config.toml` stays the other way to do it.
- Removing a folder stops its files being served at once, so tracks from it that are already queued stop playing when reached.
- No login on the UI (the user's choice). FR6 and NFR6 are the protection: the path guard limits what can be read, and the Host/Origin checks stop websites in the user's own browser from driving the service. This does not reopen the login decision.
- No default music folder (the user's choice). The service browses and plays nothing until a folder is added to `config.toml`; every place that would list or play files says so and names the file.
- Default port 8737, fixed so phone bookmarks keep working.
- Playlists are stored separately on each Mac (the user's choice). They hold absolute paths, so a playlist copied to another Mac works only where the paths match.
- Tab capture mutes the tab locally by default, which matches the user's goal of sound only from the speakers.
- MP3 320 CBR for live streams, because `x-rincon-mp3radio` is the most widely supported live format on S1.
- The service polls rather than using UPnP event subscriptions. One monitor bounds the load on the speakers.
- With the service running, `sonos play` on a file outside the music folders is an error with a config hint, rather than starting a second server. One server per Mac keeps "ours" unambiguous (from the architect's review). The user can add folders to the config.
- The extension sends rendered page HTML for detection rather than parsing it in JavaScript. One Python parser covers both paths and sees pages built by JavaScript.
- Faircamp's markup (`<audio><source type="audio/mpeg">`) is as seen on 2026-11-02. A saved fixture guards the parser.
- **Review findings not acted on**:
  - IP changes still break queued URLs (only a DHCP reservation for the Mac avoids it). Re-queuing automatically on an IP change is deferred, since it's rare on a home network.
  - Lid-closed sleep can't be prevented by an assertion; this is documented, not engineered around.
